## What the catalog is

A centralized registry of all software assets — services, libraries, data
pipelines, websites, ML models — plus the people/teams and systems around them.
Metadata lives in YAML descriptor files, conventionally **`catalog-info.yaml`**,
stored **next to the code** in each repository.

## Entity descriptor: the common envelope

Every entity, regardless of kind, has the same top-level shape:

```yaml
apiVersion: backstage.io/v1alpha1   # schema version
kind: Component                     # entity type
metadata:                           # info about the entity record
  name: artist-web
  namespace: default                # optional, defaults to "default"
  title: Artist Web                 # optional display name
  description: The place to be for artists
  labels:                           # k8s-style key/value, for filtering
    tier: "1"
  annotations:                      # link to external systems / tooling
    backstage.io/techdocs-ref: dir:.
    github.com/project-slug: acme/artist-web
  tags: [java, react]               # simple string list
  links:
    - url: https://example.com
      title: Website
spec:                               # definition — varies by kind
  type: website
  lifecycle: production
  owner: team-artist
  system: public-websites
# relations: [...]  # READ-ONLY, generated by catalog after ingestion
# status: {...}     # READ-ONLY, processing info
```

- `apiVersion` + `kind` — identify schema and type.
- `metadata` — about the record (name, labels, annotations, tags, links).
- `spec` — the actual definition; shape depends on `kind`.
- `relations` & `status` — **read-only**, filled in by the catalog after processing.

### metadata.name rules
Unique per **kind + namespace**; pattern `[a-zA-Z0-9]` with `-`, `_`, `.`
separators; **max 63 characters**.

### labels vs annotations vs tags
- **labels** — key/value, for identifying/selecting/filtering entities.
- **annotations** — key/value, non-identifying metadata linking to **external
  systems** (Git slug, PagerDuty, Grafana, TechDocs ref, Kubernetes selector).
- **tags** — plain list of strings for free-form categorization.

## Entity kinds

| Kind | Purpose | Required spec fields |
|------|---------|----------------------|
| **Component** | A unit of software (deployable/runnable) | `type`, `lifecycle`, `owner` |
| **API** | An interface exposed/consumed | `type`, `lifecycle`, `owner`, `definition` |
| **Resource** | Infrastructure (db, bucket, CDN) | `type`, `owner` |
| **System** | Group of components + resources | (`owner`) |
| **Domain** | Group of related systems (bounded context) | (`owner`) |
| **Group** | A team / org unit | — (has `members`, `parent`, `children`) |
| **User** | A person | — (has `memberOf`) |
| **Location** | Pointer to other catalog data/entities | `type`, `targets` |
| **Template** | Scaffolder template (see domain 4) | `type`, `parameters`, `steps` |

### The model hierarchy
```
Domain  ⊃  System  ⊃  Component / Resource / API
Group   ⊃  User (members);  Group parent/child
```
- **Component** `type` examples: `service`, `website`, `library`.
- **API** `type` examples: `openapi`, `asyncapi`, `graphql`, `grpc`.
- **lifecycle** examples: `experimental`, `production`, `deprecated`.
- **owner** — a single `Group` (or `User`) accountable for the entity.

### Relationships (in spec)
`owner`, `system`, `subcomponentOf`, `dependsOn`, `dependencyOf`,
`providesApis`, `consumesApis`, `parent`, `children`, `memberOf`.
These produce read-only **relations** you can query as a graph.

## Getting entities into the catalog

1. **Manual / static registration** — add a **Location** in `app-config.yaml`, or
   use the **"Register an existing component"** UI flow (paste the URL of a
   `catalog-info.yaml`).
   ```yaml
   catalog:
     locations:
       - type: url
         target: https://github.com/acme/artist-web/blob/main/catalog-info.yaml
   ```
2. **Automated discovery** — **Entity Providers** ingest entities automatically,
   e.g. **GitHub/GitLab discovery** scans repos for `catalog-info.yaml`.
3. **Location entity** — one file can point to others (`type: url` / `dir`),
   enabling hierarchical scanning.

### Processing pipeline
Ingested files are read → **processed** (validated, relations derived) →
**stitched** into the final entity. Errors surface as processing/orphan errors.

## Troubleshooting ingestion

- **Validation errors** — missing required fields (`type`, `lifecycle`, `owner`),
  bad `name` (illegal chars / too long), duplicate name+kind+namespace.
- **Owner/target not found** — referenced Group/User/System doesn't exist.
- **Orphaned entities** — the Location that created them was removed.
- Check the entity's **status** / processing errors in the UI, and backend logs.
- Refresh interval controls how often entities re-process.

## Key takeaways

- One `catalog-info.yaml` per repo, envelope = `apiVersion`/`kind`/`metadata`/`spec`.
- Kinds: Component, API, Resource, System, Domain, Group, User, Location, Template.
- Required Component fields: `type`, `lifecycle`, `owner`.
- Register via config Location, UI, or automated discovery (Entity Providers).
- `relations`/`status` are read-only; annotations link to external tools.
